# House Service Documentation

## Назначение

House Service - backend-сервис для объявлений о квартирах в домах.

Пользователь может зарегистрироваться, получить токен, создать объявление о квартире и посмотреть список квартир в доме. Модератор дополнительно может создавать дома и менять статус модерации квартиры.

Исходное задание лежит в [assignment.md](assignment.md), контракт API - в [api.yaml](../api.yaml), схема системы - в [project-structure.svg](project-structure.svg).

## Роли пользователей

В системе есть два типа пользователей:

- `client` - обычный пользователь.
- `moderator` - модератор.

Токен получается через `/login` и передается в остальные защищенные методы через `Authorization: Bearer <token>`.

## Общая схема работы

1. `cmd/main.go` читает конфигурацию, подключается к PostgreSQL и Redis.
2. PostgreSQL запускает миграции из папки `schema` при старте приложения.
3. Redis используется для кеширования токенов авторизации.
4. HTTP-ручки лежат в `internal/api`.
5. Бизнес-логика лежит в `internal/service`.
6. SQL-операции и работа с Redis лежат в `internal/store` и `internal/storage`.

Для каждого API endpoint используется отдельная папка внутри `internal/api`. Внутри папки endpoint обычно лежат:

- `handler.go` - обработчик HTTP-запроса.
- `dto.go` - входные и выходные структуры endpoint.
- `interfaces.go` - интерфейсы зависимостей endpoint.
- `conv.go` - преобразование моделей в response DTO, если endpoint возвращает JSON-модель.

## API Endpoints

### `POST /register`

Регистрирует нового пользователя.

Доступ: без авторизации.

Входные поля:

- `email` - email пользователя.
- `password` - пароль пользователя, минимум 8 символов.
- `user_type` - `client` или `moderator`.

Что делает:

1. Валидирует входные данные на уровне API.
2. Хеширует пароль через bcrypt.
3. Создает пользователя в таблице `users`.
4. Возвращает `user_id`.

Ответы:

- `200` - пользователь создан.
- `400` - невалидные данные.
- `500` - внутренняя ошибка.

### `POST /login`

Авторизует пользователя и возвращает JWT-токен.

Доступ: без авторизации.

Входные поля:

- `email` - email пользователя.
- `password` - пароль пользователя.

Что делает:

1. Валидирует email и пароль.
2. Ищет пользователя в PostgreSQL.
3. Проверяет пароль через bcrypt.
4. Если токен уже есть в Redis, возвращает существующий токен.
5. Если токена нет, создает новый JWT и сохраняет его в Redis на 24 часа.

Ответы:

- `200` - успешный логин, в ответе `token`.
- `400` - невалидные данные или неверный пароль.
- `404` - пользователь не найден.
- `500` - внутренняя ошибка.

### `POST /house/create`

Создает дом.

Доступ: только `moderator`.

Входные поля:

- `address` - адрес дома, обязательное поле, максимум 255 символов.
- `year` - год постройки, обязательное поле, не меньше 0.
- `developer` - застройщик, необязательное поле, максимум 255 символов.

Что делает:

1. Проверяет JWT.
2. Проверяет, что пользователь является модератором.
3. Валидирует входные данные.
4. Создает запись в таблице `houses`.
5. Возвращает созданный дом.

Ответы:

- `200` - дом создан.
- `400` - невалидные данные.
- `401` - пользователь не авторизован.
- `403` - пользователь не модератор.
- `500` - внутренняя ошибка.

### `POST /flat/create`

Создает квартиру в доме.

Доступ: любой авторизованный пользователь.

Входные поля:

- `number` - номер квартиры внутри дома, не меньше 1.
- `house_id` - идентификатор дома, не меньше 1.
- `price` - цена квартиры в условных единицах, не меньше 0.
- `rooms` - количество комнат, не меньше 1.

Что делает:

1. Проверяет JWT.
2. Валидирует входные данные.
3. Создает квартиру в статусе `created`.
4. Обновляет у дома поле `update_at`.
5. Возвращает созданную квартиру.

В одном доме нельзя создать две квартиры с одинаковым `number`. Такая ситуация возвращает `409 Conflict`.

Ответы:

- `200` - квартира создана.
- `400` - невалидные данные.
- `401` - пользователь не авторизован.
- `409` - квартира с таким номером в этом доме уже есть.
- `500` - внутренняя ошибка.

### `POST /flat/update`

Меняет статус модерации квартиры.

Доступ: только `moderator`.

Входные поля:

- `id` - идентификатор квартиры, не меньше 1.
- `status` - новый статус квартиры.

Разрешенные статусы:

- `on moderation`
- `approved`
- `declined`

Текущие правила переходов:

- `created` -> `on moderation`
- `on moderation` -> `approved`
- `on moderation` -> `declined`

Другие переходы считаются конфликтом. Например, нельзя сразу перевести квартиру из `created` в `approved`, и нельзя повторно взять на модерацию квартиру, которая уже в статусе `on moderation`.

Ответы:

- `200` - статус обновлен.
- `400` - невалидные данные.
- `401` - пользователь не авторизован.
- `403` - пользователь не модератор.
- `404` - квартира не найдена.
- `409` - конфликт перехода статуса.
- `500` - внутренняя ошибка.

### `GET /house/{id}`

Возвращает список квартир в доме.

Доступ: любой авторизованный пользователь.

Параметры:

- `id` - идентификатор дома, не меньше 1.

Что делает:

1. Проверяет JWT.
2. Проверяет роль пользователя.
3. Валидирует `id` дома.
4. Возвращает квартиры из таблицы `flats`.

Разница по ролям:

- `client` видит только квартиры со статусом `approved`.
- `moderator` видит квартиры в любом статусе.

Ответы:

- `200` - список квартир получен.
- `400` - невалидный `id`.
- `401` - пользователь не авторизован.
- `403` - неизвестный тип пользователя.
- `500` - внутренняя ошибка.

### `POST /house/{id}/subscribe`

Создает подписку на новые квартиры в доме.

Доступ: любой авторизованный пользователь.

Параметры:

- `id` - идентификатор дома, не меньше 1.

Входные поля:

- `email` - email для уведомлений.

Что делает сейчас:

1. Проверяет JWT.
2. Валидирует `id` дома и email.
3. Создает запись в таблице `house_subscriptions`.

Важно: сейчас реализовано только сохранение подписки. Асинхронная отправка писем при появлении новых квартир еще не реализована.

Ответы:

- `200` - подписка создана.
- `400` - невалидные данные.
- `401` - пользователь не авторизован.
- `404` - дом не найден.
- `409` - такая подписка уже существует.
- `500` - внутренняя ошибка.

## Модель данных

### `users`

Пользователи сервиса.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | `UUID` | Идентификатор пользователя. |
| `email` | `VARCHAR(255)` | Email пользователя, уникальный. |
| `password` | `VARCHAR(255)` | Хеш пароля. |
| `user_type` | `VARCHAR(255)` | Тип пользователя: `client` или `moderator`. |

### `houses`

Дома.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | Идентификатор дома. |
| `address` | `VARCHAR(255)` | Адрес дома. |
| `year` | `INT` | Год постройки дома. |
| `developer` | `VARCHAR(255)` | Застройщик дома, может быть пустым. |
| `created_at` | `TIMESTAMP` | Дата создания дома. |
| `update_at` | `TIMESTAMP` | Дата последнего добавления квартиры в дом. |

### `flats`

Квартиры.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | Идентификатор квартиры. |
| `number` | `INT` | Номер квартиры внутри дома. |
| `house_id` | `BIGINT` | Идентификатор дома. |
| `price` | `INT` | Цена квартиры в условных единицах. |
| `rooms` | `INT` | Количество комнат. |
| `status` | `flat_status` | Статус модерации квартиры. |

Ограничения:

- `house_id` ссылается на `houses.id`.
- пара `number + house_id` уникальна.

Статусы `flat_status`:

- `created`
- `on moderation`
- `approved`
- `declined`

### `house_subscriptions`

Подписки на новые квартиры в доме.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | Идентификатор подписки. |
| `house_id` | `BIGINT` | Идентификатор дома. |
| `email` | `VARCHAR(255)` | Email подписчика. |
| `created_at` | `TIMESTAMP` | Дата создания подписки. |

Ограничения:

- `house_id` ссылается на `houses.id`.
- пара `house_id + email` уникальна.

## Связи в БД

- Один дом может иметь много квартир.
- Каждая квартира относится только к одному дому.
- Один дом может иметь много подписок.
- Каждая подписка относится только к одному дому.
- Пользователи напрямую не связаны с квартирами и подписками в текущей схеме.

## Конфигурация

Конфигурация читается в `internal/service/config`.

Сначала приложение пытается загрузить `.env`, если файл существует. Затем значения читаются из переменных окружения.
Если переменная уже задана перед запуском команды, значение из `.env` ее не перетирает.

Поддерживаемые переменные:

| Переменная | Описание | Значение по умолчанию |
| --- | --- | --- |
| `SERVER_ADDRESS` | Адрес запуска HTTP-сервера. | `localhost:8080` |
| `DB_HOST` | Host PostgreSQL. | - |
| `DB_PORT` | Port PostgreSQL. | - |
| `POSTGRES_USER` | Пользователь PostgreSQL. | - |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL. | - |
| `POSTGRES_DB` | Имя базы PostgreSQL. | - |
| `REDIS_HOST` | Host Redis. | `localhost` |
| `REDIS_PORT` | Port Redis. | `6379` |
| `REDIS_PASSWORD` | Пароль Redis. | - |
| `JWT_SECRET_KEY` | Секрет для подписи JWT. | - |

`.env` не является обязательным файлом. Для Docker Compose значения берутся из `.env.example`, а `.env` может переопределить их локально.

## Локальный запуск

Скопировать пример переменных окружения:

```bash
cp .env.example .env
```

### Вариант 1. Все в Docker Compose

`.env.example` уже настроен для запуска приложения внутри Docker Compose:

```bash
docker compose up -d
```

В этом режиме приложение подключается к PostgreSQL по `DB_HOST=db`, а к Redis по `REDIS_HOST=redis`.

### Вариант 2. Зависимости в Docker Compose, приложение локально

Запустить только PostgreSQL и Redis:

```bash
docker compose up -d db redis
```

Для запуска приложения с хоста нужно переопределить в `.env`:

```env
DB_HOST=localhost
REDIS_HOST=localhost
```

После этого можно запускать приложение локально:

```bash
go run ./cmd
```
